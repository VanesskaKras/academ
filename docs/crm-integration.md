# Контракт SW CRM ↔ academ-assist worker

Версія 1.5 · 27.09.2026 (v1.1: затвердження плану — §3.5, стан `plan_review`; v1.2: `warnings` у `POST /plan` —
перевірка плану клієнта, §3.5.1; v1.3: `ready_part` серед `client_materials` і обсяг при продовженні — лише нова частина, §4;
v1.4: обсяг при продовженні — лише текст нових розділів, готова частина й дописане — один файл зі спільним списком джерел, §4;
v1.5: таблиці й рисунки готової частини переносяться у файл, нове поле `orders/{id}.readyWorkImages`; без `write_scope` розділи
для продовження беруться з коментаря, §4). Це єдине джерело правди для інтеграції. Зміни — лише через оновлення
цього файлу і погодження обох сторін. Копія лежить у обох репозиторіях (`docs/crm-integration.md`).

## 1. Принцип

CRM тримає чергу у себе. **Воркер сам приходить за роботою** (pull), генерує у своєму Firestore
своїм кодом, і **сам приносить результат** назад. CRM у Firestore не ходить і його схеми не знає.

```
CRM: статус «⚙️ Генерація» → рядок у черзі (queued)
worker: POST /jobs/claim  → job або 204            (кожні 30 с, поки є вільний слот)
worker: POST /jobs/{run_id}/progress                (≥ раз на 60 с — це і heartbeat)
worker: POST /jobs/{run_id}/result | /error         (один раз)
CRM: файли → у картку («Від команди», 🤖), статус → «На перевірку», сповіщення в топік
```

Напрямок з'єднань — лише worker → CRM (HTTPS). На сервері воркера вхідних портів немає.

## 2. Авторизація

Усі запити: `Authorization: Bearer <ACADEM_WORKER_TOKEN>`. Токен — у `.env` обох сторін, у git не потрапляє.
Базова адреса: `https://crm.studentbrains.online/api/academ`. Неправильний токен → `401`.

## 3. Ендпоінти

### 3.1 `POST /jobs/claim` — взяти наступну роботу

Тіло: `{"worker_id": "vps2-1"}` (довільний стабільний ідентифікатор інстансу).
Відповідь `204` — черга порожня. Відповідь `200`:

```json
{
  "run_id": "r_41777_3",
  "order_num": 41777,
  "kind": "large",
  "template_text": "№ замовлення - 41777\nТип - Магістерська\n⏰Дедлайн - 25.09.2026\n⚡️Напрям - Гуманітарне\n📌Тематика - Психологія\n✈️Тема - ...\n⚙️К-кість стр. - 100-120\n⚙️Унікальність - 70-80%",
  "comment": "побажання клієнта і коментар менеджера одним текстом",
  "client_plan_text": null,
  "ready_appendix_text": null,
  "practice": null,
  "files": [
    {"slot": "methodology", "name": "metodychka.pdf", "mime": "application/pdf", "size": 812345,
     "url": "https://crm.studentbrains.online/api/academ/files/<opaque-token>"},
    {"slot": "client_materials", "name": "data.xlsx", "mime": "...", "size": 12345, "url": "..."}
  ],
  "limits": {"cost_usd": 6.0, "minutes": 90},
  "deadline_at": "2026-09-25T00:00:00+03:00",
  "attempt": 1
}
```

- `kind`: `small` | `large` | `practice` (визначає CRM за типом роботи: есе/доповідь/реферат → small;
  курсова/бакалаврська/дипломна/магістерська → large; звіт з практики → practice).
- `template_text` — уже у форматі «Шаблон замовлення» (той самий, що менеджери вставляли руками).
- `comment` — те, що йде в поле «Коментар».
- `client_plan_text`, `ready_appendix_text` — текстові слоти; якщо клієнт дав план файлом — він у `files` зі слотом `client_plan`.
- `practice` — лише для `kind = practice`:
  ```json
  {"data_text": "бланк/дані практики одним текстом", "individual_task_text": "…або null",
   "place": "...", "supervisor_company": "...", "supervisor_university": "...",
   "date_from": "2026-06-01", "date_to": "2026-06-28",
   "student": "...", "group": "...", "university": "...", "faculty": "...", "department": "...",
   "specialty": "...", "degree": "...", "field": "...", "city": "..."}
  ```
  Будь-яке поле може бути `null` — воркер підтягує з `data_text` як робить UI.
- `attempt` — 1 для першого запуску, 2 — після автоповтору (див. §5). При `attempt = 2` воркер
  **продовжує** з місця зупинки (документ у Firestore той самий, `run_id` той самий).

Взяття — атомарне: одна робота видається одному воркеру один раз. Повторний `claim` того ж воркера
без завершення попередньої — повертає нову роботу (паралелізм обмежує сам воркер).

### 3.2 `GET /files/<opaque-token>` — файл слоту

Без `Authorization` (токен у самому URL, живе 24 год, після цього `410`). Віддає байти з
`Content-Type` і `Content-Disposition`. Використовується як `fileRef.url`.

### 3.3 `POST /jobs/{run_id}/progress` — прогрес + heartbeat

```json
{"stage": "writing", "pct": 45, "note": "розділ 3 з 7", "cost_usd": 1.42}
```
Надсилати **не рідше ніж раз на 60 с** під час роботи (можна без змін — це heartbeat).
`stage` — довільний рядок з конвеєра (`analysis|plan|sources|writing|appendices|docx`), `pct` 0–100,
`cost_usd` — накопичена вартість роботи. Відповідь `200 {"ok":true}` або `409` — робота вже не активна
(CRM зняв її: скасовано менеджером або визнано зависшою). На `409` воркер **зупиняє** генерацію.

### 3.4 `POST /jobs/{run_id}/result` — готово

`multipart/form-data`:
- `meta` (JSON): `{"cost_usd": 2.71, "duration_s": 2410, "pages": 104, "sections": 12, "sources": 38,
  "stages": {"analysis": 0.05, "plan": 0.12, "sources": 0.31, "writing": 2.10, "docx": 0.0}}`
- `files[]`: 1..N файлів. Основна робота — обов'язково `.docx`. Додаткові (доповідь, презентація,
  щоденник) — у тому ж запиті. Ім'я файлу — людське, без службових префіксів (CRM сам додає штамп).

Відповідь `200 {"ok":true}`. Повторний `result` для того ж `run_id` → `200 {"ok":true,"duplicate":true}`,
файли ігноруються (ідемпотентність).

### 3.5 План: затвердження в CRM (коли клієнт не дав готовий план)

Якщо у job немає `client_plan_text` і немає файлу зі слотом `client_plan`, воркер генерує план
і **зупиняється до затвердження менеджером у CRM** (не в academ-assist). Окремі ендпоінти —
без перевантаження `progress`:

`POST /jobs/{run_id}/plan` — віддати план один раз:
```json
{"plan_text": "Вступ\nРозділ 1. ...\n1.1 ...", "round": 1}
```
Відповідь `200 {"ok":true,"state":"plan_review"}`. CRM: стан `plan_review`, план у картці,
сповіщення в топік; менеджер бачить кнопки «Затвердити» / «Відредагувати й затвердити» /
«Відхилити з коментарем».

`GET /jobs/{run_id}/plan` — воркер питає раз на 60 с (це ж і heartbeat на час очікування):
```json
{"state": "pending"}
{"state": "approved", "plan_text": "…"}          // фінальний текст — МОЖЕ бути відредагований менеджером; воркер іде по ньому
{"state": "rejected", "comment": "…", "round": 2} // перегенерувати з урахуванням коментаря і знову POST /plan з round=2
```
Раундів не більше 3; після третього `rejected` → воркер шле `error` `retryable:false`.
Коментар менеджера при `rejected` воркер вносить у план через ШІ (старий план + коментар → повний новий
план) і шле його новим `POST /plan` з `round+1` — менеджер знову затверджує. Формат `plan_text` не
змінюється. Якщо ШІ не зміг внести правку, воркер шле `error` (stage `plan`), а не повторює старий план.
Час у `plan_review` **не входить** у `limits.minutes` (CRM ставить таймер на паузу) і не є
«тишею» для `stale`, поки воркер опитує `GET /plan`. Якщо менеджер не реагує 2 год — CRM
нагадує в топік; через 24 год — `error` «план не затверджено» (воркер отримає `409`).

Якщо `client_plan_text`/файл `client_plan` є — крок пропускається, воркер іде далі без зупинки,
**крім випадку, коли план клієнта не пройшов перевірку** (§3.5.1).

#### 3.5.1 Перевірка плану клієнта — `warnings` (v1.2)

Файл/текст плану клієнта часто містить не лише план (обґрунтування теми, мету, завдання, список
джерел). Воркер сам вирізає з нього план і перевіряє його кодом: чи є ≥2 розділи, чи номери
розділів і підрозділів ідуть підряд і відповідають один одному, чи немає розділів без підрозділів,
чи організація в «лапках» у плані збігається з темою. Якщо перевірка не пройшла, план іде на
затвердження тим самим `POST /plan`, але з додатковим полем:

```json
{"plan_text": "Вступ\nРозділ 1. ...", "round": 1,
 "warnings": ["У плані згадано «Нова Пошта», а в темі — «АТБ-Маркет». Перевірте, яка організація правильна."]}
```

- `warnings` — масив рядків українською, готових для показу людині; поле є **лише** коли перевірка
  не пройшла (нема поля або порожній масив — зауважень немає). Приходить тільки в `round = 1`.
- CRM показує `warnings` у картці над планом (помітно, як попередження) і в сповіщенні в топік,
  щоб менеджер виправив план через «Відредагувати й затвердити» або затвердив як є.
- Далі все як у §3.5 (`GET /plan`, раунди, таймаути) — без змін.

> **Оновлення зі сторони CRM (24.09.2026):** коли `warnings` не порожній, CRM більше НЕ надсилає
> план клієнту автоматично — ні одразу, ні пізніше по `/start`, ні по таймеру затримки (§3.5).
> Статус переходить у «Затвердження плану» з жовтим банером зауважень у картці й сповіщенням
> у чат; клієнт отримає план лише коли менеджер сам натисне «План → клієнту». Це навмисно:
> клієнт міг би затвердити помилковий план (напр. невідповідну організацію) раніше, ніж людина
> помітить попередження, і генерація пішла б за хибним планом. На ваш бік це ніяк не впливає —
> контракт `POST /plan` не змінився.

> **Для сторони CRM (реалізувати):** у `POST /jobs/{run_id}/plan` прийняти необов'язкове поле
> `warnings: string[]`, зберегти його разом з планом і показати в картці в стані `plan_review`
> (блок «⚠ Зауваження до плану клієнта» над текстом плану) та додати в сповіщення в топік.
> План з `warnings` може прийти для job, де `client_plan_text`/файл `client_plan` **є** — такий
> `POST /plan` не можна відхиляти. Поки поле не підтримано, CRM має його просто ігнорувати
> (не падати на невідомому полі).

### 3.6 `POST /jobs/{run_id}/error` — не вийшло

```json
{"stage": "sources", "message": "текст помилки для людини", "cost_usd": 0.4, "retryable": true}
```
`retryable: true` — CRM може поставити ще один автоповтор (§5); `false` — одразу до команди
(наприклад, перевищено `limits.cost_usd`, нечитабельна методичка, порожній шаблон).

## 4. Слоти файлів (категорії CRM → поля форми)

| slot | Що | Форми | Ліміт (CRM уже застосував) | small | large | practice |
|---|---|---|---|---|---|---|
| `client_plan` | план від клієнта файлом | image/pdf/docx | 1 | текст | ✓ | — |
| `methodology` | методичка | pdf/docx | ≤3 | ✓ | ✓ | ✓ |
| `example_work` | зразок роботи / структури | pdf/docx | 1 | ✓ | ✓ | ✓ (зразок звіту) |
| `diary_example` | приклад щоденника | pdf/docx | 1 | — | — | ✓ |
| `department_guidance` | скріни рекомендацій кафедри | image | ≤12 | ✓ | → `photos` | ✓ |
| `client_materials` | матеріали для аналізу/цитування | pdf/docx/txt/csv/xlsx/xml/image/код | ≤70 | ≤8 | ✓ | ✓ |
| `ready_part` | готова частина роботи | docx | 1 | ⚠ | ✓ | — |
| `client_drawings` | креслення | image | ≤4 | → `client_materials` | ✓ | — |
| `photos` | фото-контекст | image | — | ✓ | ✓ | ✓ |
| `illustrations` | ілюстрації для вставки | image/pdf | ≤5 або 1 pdf | — | ✓ | — |

Стрілка «→» — CRM уже переклав у сусідній слот, воркер отримує лише те, що для цього `kind` штатне.
`.doc` CRM віддає конвертованим у `.pdf` (оригінал не надсилається). `⚠` — надсилається, воркер сам
вирішує, чи брати.

**Готова частина роботи (v1.3, лише сторона воркера — від CRM змін не потрібно):**
- Якщо `ready_part` порожній, а серед `client_materials` є `.docx`, чиї пронумеровані заголовки (2.1, 2.1.1…)
  щонайменше двічі збігаються з планом клієнта (`client_plan_text` або файл `client_plan`) і за номером, і за
  назвою, — воркер бере цей файл як `ready_part` (у роботу як є, без переписування) і прибирає його з
  матеріалів. Без плану клієнта такого розпізнавання немає — файл лишається матеріалом.
- Якщо є готова частина (або `write_scope`), обсяг зі шаблону замовлення (к-сть сторінок) — це обсяг
  **лише тексту нових розділів**: від «Розділ N» до його кінця (підрозділи + висновки до розділу). Вступ,
  висновки, список джерел, зміст, анотація в нього не входять і дописуються понад нього (якщо їх бракує):
  готовий розділ 1 на 20 с. + «25 с.» у шаблоні = розділ 2 на 25 с. Якщо є план клієнта — розділи, яких бракує,
  беруться з нього; без плану дописуються всі відсутні розділи, зокрема ті, що стоять перед готовими.
- Результат — один `.docx`: готова частина (текст як є) + дописане в порядку плану і **один спільний список
  джерел** з наскрізною нумерацією. Джерела зі списку готової частини переносяться всі, навіть непроцитовані
  в тексті; посилання `[N]` у готовому тексті перенумеровуються під спільний список, нових посилань у готовий
  текст не додається.
- `client_plan` і `ready_part` у `.docx` читаються з номерами автонумерації Word (1.1., 1.1.1, 1.1.1.1) —
  план і заголовки можуть бути набрані списком, не лише вручну.
- (v1.5) Зміст (ЗМІСТ/CONTENTS) на початку готової частини не рахується готовими підрозділами — готовим
  вважається лише пункт, під яким є текст (кейс 41570: зміст з усім планом у файлі з розділом 1).
- (v1.5) Якщо `write_scope` не прийшов, а готова частина є, воркер бере номери розділів з коментаря
  (`comment`): «Потрібно виконати 2-й розділ» → лише розділ 2; «дописати розділи 2-3» → 2 і 3, обсяг з шаблону
  ділиться між ними. Без такої вказівки — дописується все, чого бракує за планом. `write_scope` від CRM має перевагу.
- (v1.5) Таблиці й рисунки готової частини (`ready_part`, `.docx`) переносяться у файл як є: таблиці — таблицями
  Word, рисунки — на свої місця перед підписами. Рисунки воркер витягує одразу при створенні замовлення (посилання
  §3.2 живе лише 24 год) і зберігає в документі замовлення новим полем
  `orders/{id}.readyWorkImages: [{name, type, b64} | null]` — індекс N відповідає рядку-маркеру
  `[ГОТОВА-ЧАСТИНА-РИСУНОК:N]` у `readyWorkText`/`content`. Рисунки стискаються (≤1400 px) і разом займають
  ≤~600 КБ; що не вмістилось або не читається (EMF/WMF) — `null`, у роботі лишається підпис, у лог — попередження.
  Від CRM змін не потрібно.

> **Для сторони CRM (перевірити):** у замовленні 41476 готова частина роботи (готовий розділ 2) дійшла до воркера
> **не** слотом `ready_part` — схоже, вона прийшла в `client_materials`. Тому її переписали заново, а посилання
> з її тексту («[14 с.39; 15 с.214]») потрапили в список джерел. Треба перевірити весь ланцюжок:
> 1. Файл, який менеджер позначив у CRM як «Готова частина роботи», потрапляє в `job.files` саме з
>    `"slot": "ready_part"`, а не `client_materials` (перевірити мапінг категорії CRM → slot і що
>    для `kind: "large"` цей слот не відфільтровується і не зливається з матеріалами).
> 2. Його `url` (§3.2) віддає сам `.docx` (не порожній і не HTML-сторінку помилки), а `name`/`mime` вказують
>    на docx (`.docx` або `application/vnd.openxmlformats-officedocument.wordprocessingml.document`).
> 3. `.doc`, позначений як готова частина, приходить конвертованим — але в PDF воркер `ready_part` не
>    розбирає (лише docx); такий випадок має або конвертуватися в docx, або явно повідомлятись менеджеру.
> 4. Файл надсилається в `ready_part` лише один раз, і той самий файл не дублюється ще й у `client_materials`.
>
> Як перевірити з боку воркера: у лозі створення замовлення має бути або
> «✓ Готову частину роботи отримано слотом ready_part (…)», або
> «✓ Файл … з client_materials розпізнано як готову частину роботи» (запасний варіант v1.3). Якщо є лише
> другий рядок, CRM надіслав готову частину не тим слотом.

> **Відповідь зі сторони CRM (23.09.2026):** перевірено весь ланцюжок на замовленні 41476 — файл
> `^N41370 (2)-...docx` у БД має `category=ready_part` (виставлено ще до старту генерації), `applicability()`

> автонумерації Word на боці воркера, а не в передачі слоту. Якщо побачите цей симптом ще раз —
> киньте `run_id`, звіримо конкретний payload `POST /jobs/claim`, а не історичний запис у БД.

## 5. Життєвий цикл, таймаути, повтори

| Стан у CRM | Що це |
|---|---|
| `queued` | менеджер перевів у «Генерація»; чекає воркера |
| `running` | взято воркером; є heartbeat |
| `plan_review` | план згенеровано, чекає менеджера в CRM (§3.5); таймер `limits.minutes` на паузі |
| `stale` | тиша > 10 хв → CRM повертає в `queued` з `attempt = 2` **один раз**; друга тиша → `error` |
| `done` | результат прийнято; файли в картці; статус замовлення → «На перевірку» |
| `error` | причина в картці + алерт у топік; кнопка «Повторити» = новий `run_id`, `attempt = 1` |

- Ліміт часу на роботу — `limits.minutes` (90); після нього CRM ставить `stale`.
- Ліміт вартості — `limits.cost_usd`; воркер зупиняється сам і шле `error` з `retryable:false`.
- Автоповтор лише один, і лише з продовженням (не з нуля). Усе інше — руками через «Повторити».
- Скасування менеджером: наступний `progress` отримує `409` — воркер зупиняється, нічого не шле.

## 7. Що НЕ входить у контракт

Схема `orders/{id}` у Firestore, промпти, моделі, кроки конвеєра, формат `.docx` — повністю сторона
academ-assist. CRM бачить лише §3. Обмеження одне: headless-результат має збігатися з тим, що дає
кнопка в UI на тому самому замовленні.

## 8. Перевірка перед пілотом (чек-лист)

1. `claim` на порожній черзі → `204`.
2. Тестове замовлення → `claim` віддає job з `files[].url`, кожен URL качається без авторизації.
3. `progress` кожні 60 с; штучне «мовчання» 10 хв → CRM повертає в чергу з `attempt=2`, воркер продовжує.
4. `result` з `.docx` → файл у картці, статус «На перевірку»; повторний `result` → `duplicate:true`.
4a. Замовлення без плану клієнта → `POST /plan` → у картці план і кнопки; «Відхилити» з коментарем →
    воркер надсилає план `round=2`; «Відредагувати й затвердити» → `GET /plan` повертає змінений текст,
    робота написана саме за ним.
4b. Замовлення з файлом плану, де план серед іншого тексту і з помилкою (напр. інша організація, ніж
    у темі) → `POST /plan` з `warnings` → у картці план + блок зауважень, сповіщення в топік.
5. `error` `retryable:false` → алерт у топік, кнопка «Повторити» в картці.
6. Той самий заказ через UI-кнопку і через воркер → однаковий `.docx` (структура, обсяг, джерела).
